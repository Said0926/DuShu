# Dúshū — правила проекта

Веб-приложение для изучения китайского языка. Пользователь вставляет китайский текст и получает
два режима: **«Чтение»** (пиньинь над иероглифами через `<ruby>`, перевод предложений, словарные
подсказки при наведении) и **«Shadowing»** (озвучка с караоке-подсветкой и паузами для повторения).

Стек: Python 3.12, Django 5.x, PostgreSQL, django-allauth, django-environ, django-ratelimit,
jieba, pypinyin, Django templates + vanilla JS (без React/Vue и без HTMX), pytest + pytest-django,
Docker, ruff, pre-commit, GitHub Actions.

Проект учебный и портфолийный. Владелец — junior-разработчик, которому важно понимать каждую строчку.
Поэтому: простой читаемый код вместо «умного», минимум абстракций, объяснения на русском после
каждого шага. Если видно решение лучше запрошенного — сказать до того, как писать код.

## Команды

**Всё выполняется внутри контейнера.** Локально установлен Python 3.10 — проекту нужен 3.12,
вне Docker он не запустится.

```bash
docker compose up -d                                   # поднять web + postgres
docker compose logs -f web                             # логи
docker compose exec web python manage.py <command>     # любая manage-команда
docker compose exec web pytest                         # тесты
docker compose exec web pytest tests/chinese -v         # тесты одного app
docker compose exec web ruff check .                   # линтер
docker compose exec web ruff format .                  # форматтер
docker compose down                                    # остановить
```

Импорт словарей (после этапа 4):

```bash
docker compose exec web python manage.py import_cedict <path>
docker compose exec web python manage.py import_bkrs <path>
```

## Архитектура

Главное требование — расширяемость. Впереди личные словари с интервальным повторением,
статистика, уровни HSK. Правила, которые это обеспечивают:

- **Фича = отдельный Django app**, все apps лежат в пакете `apps/`.
- **Бизнес-логика в `services.py`** (или пакете `services/`), views тонкие: разобрать запрос,
  вызвать сервис, отдать ответ. Логики в шаблонах нет.
- **Внешние API — только через провайдеры.** Абстрактный базовый класс + конкретные реализации,
  выбор через путь к классу в settings и `import_string`. Никаких прямых вызовов `requests`
  из views или сервисов фичи.
- **Общая обработка китайского текста живёт в `apps/chinese`** и используется всеми фичами.
  У этого app нет моделей и нет URL — только сервисы.
- **Языки перевода расширяемы.** Поле `language` — обычный `CharField` **без `choices`**:
  добавление языка не должно требовать миграции. Допустимые значения берутся из
  `settings.TRANSLATION_LANGUAGES`, проверяются в формах и сервисах.
- **Всё, что стоит денег, кэшируется в БД**: переводы предложений (ключ — хэш предложения + язык),
  аудио и тайминги. Повторное открытие текста не должно вызывать новых запросов к API.
- **Ошибка внешнего API не роняет страницу.** Логируем, показываем понятное сообщение, рендерим
  то, что можем.

Карта apps:

| App | Зона ответственности |
|---|---|
| `core` | главная, `base.html`, context processors |
| `accounts` | `User(AbstractUser)`, `UserSettings`, профиль |
| `chinese` | разбиение на предложения, сегментация, пиньинь, тоны |
| `dictionary` | `DictionaryEntry`, импорт словарей, поиск |
| `translation` | `TranslationProvider`, кэш переводов |
| `tts` | `TTSProvider`, кэш аудио и таймингов |
| `reader` | страница «Чтение» |
| `shadowing` | страница «Shadowing» |
| `library` | сохранённые тексты пользователя |

Зависимости идут только в одну сторону: фичи (`reader`, `shadowing`, `library`) зависят от
инфраструктуры (`chinese`, `dictionary`, `translation`, `tts`), но не друг от друга.

## Дизайн

Источник правды — `design/DESIGN.md` и `design/tokens.css`. Эти файлы **не редактируем**,
они справочник. Рабочая копия токенов — `static/css/tokens.css`, подключается первой.

- Только `var(--...)`. Хардкод-хексов в компонентных стилях нет.
- Никакого инлайн-CSS и никаких стилей внутри JS. **JS меняет только классы и `data-`атрибуты.**
- Файлы стилей: `tokens.css` (переменные), `base.css` (каркас интерфейса),
  `text.css` (разметка китайской строки — нужна трём страницам сразу), `home.css`,
  `reader.css`, `shadowing.css`. Первые три подключены в `base.html`, остальные — через
  блок `extra_css`.
- Класс тона (`tone-1`…`tone-5`) вешается на `<span>` внутри `<ruby>`, не на `<rt>` и не на слово.
- Каждое слово — `<button type="button" class="word" data-word data-pinyin>`: работает Tab
  и скринридер, и есть готовая зацепка для будущей кнопки «в мой словарь».
- Знаки препинания — отдельный `<span class="punct">`, внутрь слова не попадают.
- Настройки страницы переключают классы на контейнере (`pinyin-off`, `tones-off`,
  `translation-off`, `hints-off`), а не перерисовывают текст.
- Адаптив: брейкпоинт 900px, минимальная интерактивная цель 44px.
- Доступность: `role="switch"` + `aria-checked` у переключателей, `aria-pressed` у сегментов,
  `aria-label` у иконочных кнопок, видимый фокус.

## Соглашения по коду

- Код, имена и docstrings — **на английском**. Комментарии — **на русском**, и только там,
  где логика неочевидна.
- Docstrings у классов и функций, Google style.
- Type hints на всех функциях и нетривиальных переменных. PEP 8 строго.
- f-strings, `pathlib` вместо `os.path`, `dataclass` для простых контейнеров.
- Никогда: голый `except` (ловим конкретное исключение с внятным сообщением), `print()`
  в рабочем коде (только `logging`), секреты в коде (только из `.env`).
- Тесты: pytest + pytest-django. Проверяем не только happy path, но и краевые случаи
  и пути с ошибками. Фикстуры словарей маленькие, реальные дампы в тесты не тащим.
