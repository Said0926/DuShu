# Dúshū — правила проекта

Веб-приложение для изучения китайского языка. Пользователь вставляет китайский текст и получает
два режима: **«Чтение»** (пиньинь над иероглифами через `<ruby>`, перевод предложений, словарные
подсказки при наведении) и **«Shadowing»** (озвучка с караоке-подсветкой и паузами для повторения).

Стек: Python 3.12, Django 5.x, PostgreSQL, django-allauth, django-environ, django-ratelimit,
jieba, pypinyin, edge-tts, Django templates + vanilla JS (без React/Vue и без HTMX), pytest + pytest-django,
Docker, ruff, pre-commit, GitHub Actions.

Проект учебный и портфолийный. Владелец — junior-разработчик, которому важно понимать каждую строчку.
Поэтому: простой читаемый код вместо «умного», минимум абстракций, объяснения на русском после
каждого шага. Если видно решение лучше запрошенного — сказать до того, как писать код.

## Команды

**Всё выполняется внутри контейнера.** Локально установлен Python 3.10 — проекту нужен 3.12,
вне Docker он не запустится.

```bash
docker compose up -d                                   # поднять web + postgres
docker compose logs -f web                             # логи
docker compose exec web python manage.py <command>     # любая manage-команда
docker compose exec web pytest                         # тесты
docker compose exec web pytest tests/chinese -v         # тесты одного app
docker compose exec web ruff check .                   # линтер
docker compose exec web ruff format .                  # форматтер
docker compose down                                    # остановить
```

Импорт словарей (после этапа 4):

```bash
docker compose exec web python manage.py import_cedict <path>
docker compose exec web python manage.py import_bkrs <path>
```

## Перевод

Провайдер задаётся в `.env` путём к классу:

```bash
TRANSLATION_PROVIDER=apps.translation.providers.deepl.DeepLProvider   # нужен DEEPL_API_KEY
TRANSLATION_PROVIDER=apps.translation.providers.dummy.DummyProvider   # заглушка, без ключа
```

Ключ DeepL Free выглядит как `279a2e9d-83b3-c416-7e2b-f371d29d3caa:fx` — 36 символов
плюс суффикс `:fx`. Берётся в аккаунте DeepL: Account → API Keys.

Все переводы кэшируются в `SentenceTranslation` по хэшу предложения и языку,
поэтому повторное открытие текста бесплатно.

Обратная сторона кэша: попадание в него никогда не доходит до провайдера. Если
в кэше остались заглушки от `DummyProvider`, после подключения ключа их нужно
сбросить, иначе они так и будут показываться:

```bash
docker compose exec web python manage.py clear_translation_cache --provider DummyProvider
```

## Озвучка и Shadowing

Провайдер задаётся путём к классу, как у перевода:

```bash
TTS_PROVIDER=apps.tts.providers.edge.EdgeTTSProvider   # по умолчанию, бесплатно и без ключа
TTS_PROVIDER=apps.tts.providers.dummy.DummyTTSProvider # тишина, для работы без сети
TTS_VOICE=zh-CN-XiaoxiaoNeural                         # список: edge-tts --list-voices
```

`edge-tts` — **неофициальный** клиент к тому движку, которым Edge читает страницы вслух.
Голоса и тайминги там те же, что продаёт Azure: это один движок. Плата за бесплатность —
эндпоинт иногда отвечает 503 или отдаёт пустой поток. Это переживаемо ровно потому, что всё
кэшируется: сбой стоит первого открытия одного текста, а не самой фичи. Переход на Azure —
один новый класс и строка в `.env`.

**Озвучка идёт по предложениям**, ключ кэша — хэш предложения плюс голос. Отсюда: фраза,
общая двум текстам, озвучивается один раз; правка одного предложения не обнуляет остальные;
а в плеере повтор — это `currentTime = 0`, пауза — «не запускать следующее». Скорости в ключе
нет: аудио всегда нормальное, скорость делает `playbackRate` у `<audio>`.

Синтез всего текста происходит при открытии страницы, параллельно (`TTS_CONCURRENCY`, по
умолчанию 4). Поэтому длительности в списке предложений сразу верные, а плеер полностью
синхронный — ни одной гонки между загрузкой и воспроизведением. Обратная сторона: текст на
сотню предложений при первом открытии заставит ждать десятки секунд.

**Тайминги хранятся как позиции символов**, а не индексы слов. Слова существуют только
благодаря jieba: обновится его словарь — сегментация сдвинется, и кэш начнёт молча
подсвечивать не те слова. Символы не сдвигаются, поэтому раскладка по словам пересчитывается
при каждом рендере (`apps/tts/alignment.py`).

Две вещи, на которых уже обожглись:

- **`boundary="WordBoundary"` у `Communicate` обязателен явно.** По умолчанию там
  `SentenceBoundary`, и караоке начнёт подсвечивать предложения целиком — без единой ошибки.
- **Подсветку нельзя вешать на `timeupdate`.** Событие приходит ~4 раза в секунду, а
  односложное слово звучит ~120 мс: по замерам 我 (125 мс) и 去 (113 мс) не подсвечивались
  вообще ни разу. Плеер обновляет подсветку по `requestAnimationFrame`.

Границы слов от Microsoft **не совпадают с jieba**: 在哪儿 приходит одним событием там, где
jieba видит 在 и 哪儿. Поэтому слово берёт минимальный старт и максимальный конец среди
перекрывающих его событий, а сами события раскладываются поиском от курсора — счётом длин
нельзя, сегментатор выбрасывает пробелы.

Аудио лежит файлами в `MEDIA_ROOT`, метаданные и тайминги — в базе. Аудио производно, его
можно потерять и пересоздать; тайминги без него бесполезны, а он без них — просто звук.
**При деплое `media/` должен стать именованным томом или уехать в S3**, иначе пересоздание
контейнера сотрёт кэш.

Заглушки от `DummyTTSProvider` сбрасываются так же, как заглушки переводов, и по той же
причине — попадание в кэш до провайдера не доходит, а молчащий текст сбивает с толку сильнее
неточного перевода:

```bash
docker compose exec web python manage.py clear_audio_cache --provider DummyTTSProvider
docker compose exec web python manage.py clear_audio_cache --voice zh-CN-XiaoxiaoNeural
```

Команда удаляет и файлы: Django при удалении строки файл не трогает, и массовое удаление
забило бы `media/` сиротами.

## Авторизация и лимиты

Вход по email и паролю или через Google, всё на django-allauth.

**Подтверждение почты обязательно.** Дело не в чистоте базы: у зарегистрированных лимит
обработок выше, чем у гостей, и без подтверждения «регистрация» стоила бы выдуманного адреса
и десяти секунд, то есть повышенный лимит выдавался бы кому угодно сколько угодно раз.

В разработке письма никуда не уходят — `EMAIL_BACKEND` печатает их в лог контейнера:

```bash
docker compose logs -f web                    # письмо целиком
# только ссылка из последнего письма:
docker compose logs web | grep -o 'http://localhost:8000/accounts/confirm-email/[^ ]*' | tail -1
```

Ссылку всегда можно получить заново: попробуй войти неподтверждённым аккаунтом — не пустят,
но новое письмо уйдёт в лог.

**Google** настраивается ключами в `.env` (`GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`), а не
строкой `SocialApp` в админке: секреты не уезжают в базу. Пока ключей нет, секция `APP`
в настройках не создаётся, провайдер не попадает в список и кнопка не рисуется вовсе.
Redirect URI для консоли Google: `http://localhost:8000/accounts/google/login/callback/`.

`SOCIALACCOUNT_EMAIL_AUTHENTICATION` включён: зарегистрировавшийся по паролю может потом
войти через Google с тем же адресом. По умолчанию это выключено, потому что провайдер,
врущий про подтверждённость адреса, вошёл бы в любой чужой аккаунт. **Появится второй
провайдер — решение пересмотреть.**

**Настройки чтения** для гостя лежат в `localStorage`, для авторизованного — в `UserSettings`.
Их рендерит сервер прямо в разметку: иначе страница успевает отрисоваться с умолчаниями
и дёргается, когда браузер прочитает сохранённые значения. Пустой `font_size` означает
«не выбирали» и это не то же самое, что `md`: без атрибута `data-size` на узком экране
действует уменьшенный кегль из медиазапроса.

**Лимиты** — в `apps/core/limits.py`, числа в settings: гость `5/h`, пользователь `30/h`
на обработку текста, столько же отдельной группой на озвучку, подсказки словаря считаются
отдельно и мягче. Лимит на озвучку стережёт не деньги (edge-tts бесплатен), а репутацию
у неофициального эндпоинта и процессор. Читать счётчик нужно
той же группой, ключом и ставкой, какими он пишется, иначе шапка покажет число, не имеющее
отношения к действующему лимиту, и никто об этом не сообщит.

Лимит считает **платную работу, а не запросы**. Перед обработкой проверяем
`has_cached_translations()`: если все предложения уже в кэше, провайдер не вызывается
и счётчик не трогается. Поэтому проверка живёт в самом view, а не в декораторе —
декоратор увеличивает счётчик до того, как станет известно, платный это запрос или нет.
Обратная сторона: перечитывать закэшированный текст можно сколько угодно, и от нагрузки
на процессор это не защищает. Так задумано — лимит стережёт бюджет переводчика, а частоту
запросов в проде ограничивает прокси.

Счётчики живут в `LocMemCache`, то есть в памяти процесса. Упёрся в собственный лимит
при проверках — сбрось:

```bash
docker compose restart web
```

## Библиотека, подборки и прогресс

Подборки бывают двух видов, и различает их **пустой владелец**:

- **общие уровни HSK** — `owner` пустой, видны всем, создаются миграцией данных
  (`library/0003_hsk_collections.py`). Переименовать и удалить их через сайт нельзя;
- **свои подборки** — принадлежат одному человеку.

Тексты устроены так же: пустой `owner` означает каталожный текст, общий для всех.
Заводить такие можно только через админку — наполнение уровней HSK делает владелец проекта,
а не читатели.

Из этого следует приятная вещь: подборка может быть общей, а текст в ней — личным. То есть
свои тексты можно раскладывать по уровням HSK, и видеть их будет только их владелец.

**Прогресс чтения — отдельная модель**, а не поле у текста. Каталожный текст это одна строка
на всех, и поле статуса на ней было бы одним статусом на всех. Отсутствие записи означает
«не прочтён»: статусы пишутся только когда их меняют, поэтому таблица растёт по активности,
а не как «тексты × пользователи».

Правил доступа ровно два, и оба живут в `services.py`, а не во views:

- **видимость** — своё плюс общее (`owner=user | owner IS NULL`);
- **владение** — менять можно только своё; общее не меняет через сайт никто.

Удаление подборки **не удаляет тексты** — связь `SET_NULL`, тексты оказываются
«Без подборки». Терять месяц чтения из-за уборки в папках недопустимо.

Переключатель статуса стоит и в библиотеке, и в шапке «Чтения». Чтобы `reader` при этом
не зависел от `library`: подписи статусов приходят context processor'ом, адрес сохранения —
через `{% url %}`, а id и текущий статус — скрытыми полями формы «Читать». Ни одного импорта
из `library` в `reader` нет.

Добавить HSK 6 — это строка в `HSK_LEVELS` и маленькая миграция данных. Уровни намеренно
не захардкожены пятёркой: в стандарте HSK 3.0 их девять.

## Архитектура

Главное требование — расширяемость. Впереди личные словари с интервальным повторением,
статистика, уровни HSK. Правила, которые это обеспечивают:

- **Фича = отдельный Django app**, все apps лежат в пакете `apps/`.
- **Бизнес-логика в `services.py`** (или пакете `services/`), views тонкие: разобрать запрос,
  вызвать сервис, отдать ответ. Логики в шаблонах нет.
- **Внешние API — только через провайдеры.** Абстрактный базовый класс + конкретные реализации,
  выбор через путь к классу в settings и `import_string`. Никаких прямых вызовов `requests`
  из views или сервисов фичи.
- **Общая обработка китайского текста живёт в `apps/chinese`** и используется всеми фичами.
  У этого app нет моделей и нет URL — только сервисы.
- **Языки перевода расширяемы.** Поле `language` — обычный `CharField` **без `choices`**:
  добавление языка не должно требовать миграции. Допустимые значения берутся из
  `settings.TRANSLATION_LANGUAGES`, проверяются в формах и сервисах.
- **Всё, что стоит денег, кэшируется в БД**: переводы предложений (ключ — хэш предложения + язык),
  аудио и тайминги. Повторное открытие текста не должно вызывать новых запросов к API.
- **Ошибка внешнего API не роняет страницу.** Логируем, показываем понятное сообщение, рендерим
  то, что можем.

Карта apps:

| App | Зона ответственности |
|---|---|
| `core` | главная, `base.html`, context processors, конфигурация лимитов |
| `accounts` | `User` (вход по email), `UserSettings`, профиль, формы allauth |
| `chinese` | разбиение на предложения, сегментация, пиньинь, тоны |
| `dictionary` | `DictionaryEntry`, импорт словарей, поиск |
| `translation` | `TranslationProvider`, кэш переводов |
| `tts` | `TTSProvider`, выравнивание таймингов, кэш аудио |
| `reader` | страница «Чтение» |
| `shadowing` | страница «Shadowing»: сцена, список предложений, плеер |
| `library` | `SavedText`, `Collection`, `ReadingProgress`, подборки и прогресс |

Зависимости идут только в одну сторону: фичи (`reader`, `shadowing`, `library`) зависят от
инфраструктуры (`chinese`, `dictionary`, `translation`, `tts`, `accounts`, `core`),
но не друг от друга.

## Дизайн

Источник правды — `design/DESIGN.md` и `design/tokens.css`. Эти файлы **не редактируем**,
они справочник. Рабочая копия токенов — `static/css/tokens.css`, подключается первой.

- Только `var(--...)`. Хардкод-хексов в компонентных стилях нет.
- Никакого инлайн-CSS и никаких стилей внутри JS. **JS меняет только классы и `data-`атрибуты.**
- Файлы стилей: `tokens.css` (переменные), `base.css` (каркас интерфейса),
  `text.css` (разметка китайской строки — нужна трём страницам сразу), `home.css`,
  `reader.css`, `shadowing.css`. Первые три подключены в `base.html`, остальные — через
  блок `extra_css`.
- Класс тона (`tone-1`…`tone-5`) вешается на `<span>` внутри `<ruby>`, не на `<rt>` и не на слово.
- Каждое слово — `<button type="button" class="word" data-word data-pinyin>`: работает Tab
  и скринридер, и есть готовая зацепка для будущей кнопки «в мой словарь».
- Знаки препинания — отдельный `<span class="punct">`, внутрь слова не попадают.
- Настройки страницы переключают классы на контейнере (`pinyin-off`, `tones-off`,
  `translation-off`, `hints-off`), а не перерисовывают текст.
- Адаптив: брейкпоинт 900px, минимальная интерактивная цель 44px.
- Доступность: `role="switch"` + `aria-checked` у переключателей, `aria-pressed` у сегментов,
  `aria-label` у иконочных кнопок, видимый фокус.

## Проверка вёрстки

Скриншоты снимаются установленным Chrome, ставить ничего не нужно:

```bash
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless --disable-gpu \
  --screenshot=/tmp/shot.png --window-size=1440,900 --virtual-time-budget=4000 \
  http://localhost:8000/reader/
```

Две ловушки, на которые уже попадались:

- **Chrome не делает окно уже 500px.** Скриншот с `--window-size=375` покажет страницу,
  отрисованную на 500px, просто обрезанную, и это выглядит как переполнение вёрстки.
  Для честной проверки адаптива страница грузится в `<iframe width="375">` на широкой
  странице-обёртке.
- **Страницу с результатом не получить через GET.** Ответ сохраняется curl-ом с CSRF-токеном
  во временный файл внутри `static/`, открывается по `/static/...` (тогда пути к CSS рабочие)
  и удаляется сразу после проверки.

Интерактив (переключатели, подсказки) проверяется скриптом-зондом, который дописывается
в сохранённый HTML: он кликает по элементам и печатает результат на страницу.

## Соглашения по коду

- Код, имена и docstrings — **на английском**. Комментарии — **на русском**, и только там,
  где логика неочевидна.
- Docstrings у классов и функций, Google style.
- Type hints на всех функциях и нетривиальных переменных. PEP 8 строго.
- f-strings, `pathlib` вместо `os.path`, `dataclass` для простых контейнеров.
- Никогда: голый `except` (ловим конкретное исключение с внятным сообщением), `print()`
  в рабочем коде (только `logging`), секреты в коде (только из `.env`).
- Тесты: pytest + pytest-django. Проверяем не только happy path, но и краевые случаи
  и пути с ошибками. Фикстуры словарей маленькие, реальные дампы в тесты не тащим.

## Git

Репозиторий: `git@github.com:Said0926/DuShu.git` (SSH, ключ `~/.ssh/id_ed25519`).
В коммитах — noreply-адрес GitHub, личная почта в историю не попадает.

Каждый этап живёт в своей ветке и вливается через pull request:

```bash
git checkout -b stage-3-chinese     # в начале этапа
# ... работа, коммиты по ходу ...
git push -u origin stage-3-chinese  # в конце этапа
```

Дальше pull request создаётся и мержится через веб-интерфейс — `gh` CLI не установлен.
Мержим только после зелёного CI: GitHub Actions прогоняет ruff и pytest на каждый PR,
поэтому сломанный код в `main` не попадает. После мержа:

```bash
git checkout main && git pull
```

Правила коммитов:

- Сообщения на английском, описательные. Первая строка — что сделано, дальше абзац о том,
  **почему** именно так, если решение неочевидное.
- Одно логическое изменение на коммит. Не смешивать несвязанное.
- Никогда не коммитить `.env`, дампы словарей, `__pycache__`, кэши инструментов.
- Перед коммитом прогнать `ruff` и `pytest` — красный код в ветку не уезжает.

## Чего не делать без явной просьбы

- Менять или удалять `.env`
- Удалять и переписывать существующие миграции
- Трогать логику авторизации и безопасности
- Мержить pull request (создать ветку и запушить — можно, это согласованный workflow;
  нажать Merge — только владелец)
- Делать force push и переписывать уже опубликованную историю
- Ставить новые зависимости, не перечислив и не объяснив их сначала
- Удалять любые файлы

## Лицензии словарей

- **CC-CEDICT** — CC BY-SA 4.0 (версия указана в шапке самого дампа; на сайте проекта
  до сих пор написано 3.0). Атрибуция обязательна: в подвале сайта и в README.
- **БКРС** — правообладатели разрешают: «Базы можно использовать свободно в любых целях.
  Можно указать данный сайт как источник» (bkrs.info/p47). Это не формальная OSI-лицензия,
  а явное разрешение. Атрибуцию ставим. При коммерческом использовании стоит написать им.

Дампы качаются вручную в `data/` (папка в `.gitignore`):

```bash
curl -L -o data/cedict.txt.gz \
  https://www.mdbg.net/chinese/export/cedict/cedict_1_0_ts_utf-8_mdbg.txt.gz
curl -L -o data/dabkrs.gz https://bkrs.info/downloads/daily/dabkrs_<ГГММДД>.gz

docker compose exec web python manage.py import_cedict data/cedict.txt.gz
docker compose exec web python manage.py import_bkrs data/dabkrs.gz
```

Обе команды читают `.gz` без распаковки и безопасны при повторном запуске.
Флаг `--replace` нужен при обновлении дампа: без него изменившиеся записи
будут отброшены как дубликаты, а устаревшие останутся.
